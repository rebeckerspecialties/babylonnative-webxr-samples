# Quest WebXR qualification

Build the ARM64 qualification APK using the committed submodules, not a system BabylonNative checkout. See [the build workflow](.github/workflows/android-apk.yml) and [runtime handoff](third_party/BabylonNative/Documentation/QuestRuntimeHandoff.md). Keep hosted simulator screenshots off. Use ordinary device logging; separately check Home, tracking and physical passthrough after exit.

- **Pixels:** `python android/test-layers.py --capture OUT SERIAL 118 25 26 27 28 105 106 107 108` (OpenCV). Require the two projection eyes, color/depth silhouettes, stereo film markers and transparent/opaque foreground controls. Cases 109/110 exercise silent 24 fps film; 10/11 exercise the original 30 fps film. FFmpeg reference pixels, display capture and headset inspection answer different questions.
- **Pacing:** `python android/test-layers.py --log RUN.log --pacing SERIAL 111 112 113 114`. Actual 24 fps film at 72 Hz, then 30 at 60 Hz, texture before direct. No capture or sampling. After 2 s warmup count missed **predicted refreshes**, longest unbroken interval and steady rate. One missed interval fails the full-window gate. Use 3-6 and 115-118 for mono/stereo stills, 7 for combined layers. Run 9 separately: it needs a real select event.
- **Interactive control:** `python android/capture-interactive-layer.py SERIAL 10 --timing-only` keeps the real Babylon controller projection/HUD. Use 3 for the photograph and 11 for direct media. Supply a screenshot path **instead** of timing mode to inspect controller occlusion. Do not infer interactive performance from the raw cases.
- **Input Selection:** interactive Run uses tracked cameras; the automated score uses synthetic cameras. Launch with `--ez selectionBenchmark true --ez trackedSelection true --ez validateDensity true` to check actual 4x MSAA eye attachments: both centers retain 240 edges, both peripheries change 240/0/240 at off/max/off. Keep readback out of timing runs. Use `--ez hoverSweep true` separately for the 72 Hz Run/Next stock/optimized/stock ray replay.
- **VP9:** On page 11 add `--reference-grip --vp9-profile 0 --film-fps 24` (or 30) to inspect the Android decoder Surface. In a separate screenshot run require red left and blue right; in the timing run add `--pacing`. Profile 2 at 24 fps is a hardware capability test, not an expected pass on Quest 1. Keep the decoder clock gate even if XR frames advance.
- **Limits:** See [device measurements](qualification/quest-1/pacing.md). Direct media uses a compositor Surface. Texture video uses a conversion/upload fallback when [actual decoder buffers cannot be sampled](third_party/BabylonNative/Core/GraphicsWgpu/Tests/AndroidDecoderImport.md). The iPhone AR portal is a separate application; it does not qualify these VR samples on iOS.
